# Правила IAD: содержание, взаимодействие и построение

Это единый нормативный документ IAD. Он сохраняет исходные требования и уточнения,
полученные при работе с картой `lab-engine`, включая одобренные возможности.
Его можно использовать как системную инструкцию агенту вместе с каталогом проекта
и схемами. В IAD Kit интерфейс уже реализован: агент заполняет данные, а новые
возможности ядра выполняются отдельной задачей. Формулировки «построй», «покажи» и
«реализуй» ниже задают требуемое поведение результата и не требуют заново писать UI.

Каркас поддерживает объяснения по коду, сравнение готовых моделей и парную сборку
двух подготовленных IAD-проектов. Автоматическая запись трасс и восстановление
архитектуры произвольного Git diff
остаются требованиями к будущим адаптерам. Не выдавай их за реализованные возможности.

При явном запросе на построение карты создай по указанным репозиториям интерактивную IAD на HTML и JavaScript. При первом открытии владелец проекта должен видеть устройство системы и несколько готовых сценариев, выбирать любой из них и прослеживать его по коду.

### Данные для запуска

```text
Репозитории и версии: <путь или URL и Git ref для каждого>
Таргет: <класс | модуль | репозиторий | набор репозиториев> <имя>
Приоритетные сценарии: <перечень или «подбери по коду»>
Сравнение: <исходная и целевая версии либо «только карта»>
Цветовая тема: <предпочтения владельца либо «подбери для читаемости»>
```

## 0. Разделяй развитие инструмента и построение карты

IAD — общий инструмент. Репозиторий каркаса содержит просмотрщик, сборщик, схемы,
пустую заготовку, правила и проверки. Готовые карты, их участники, сценарии, исходники
изучаемых проектов и результаты сборки хранятся во внешних каталогах диаграмм.
Пустая заготовка `iadkit/templates/project/` не содержит предписанных модулей,
связей, операций или сценариев. Её использует `init`, заполняя только заданные
метаданные и закреплённую версию источника.

Если задача — усовершенствовать IAD, разбирай предъявленную диаграмму как материал
проверки правил, схем и визуализации. Исправляй общий класс ошибки в шаблоне,
просмотрщике или валидаторе. Изменение, заполнение или пересборка конкретной карты
выполняется по отдельному явному запросу. При проверке общих механизмов используй
временные тестовые модели; реальные проекты не должны быть встроены в ядро,
пустую заготовку, начальные сценарии или обязательные проверки каркаса.

Если задача — построить или обновить конкретную IAD, создай отдельный внешний
каталог из пустой заготовки и заполни его по фактическому коду. Общие имена модулей,
количество узлов и сценарии определяет изучаемый проект. Примеры в этом документе
иллюстрируют правила и не задают содержимое новой карты. Явно различай выбор
пользовательских входов: UI — действия интерфейса, API — запросы и события,
CLI — команды, библиотека — операции вызывающего кода. Полноценный пользовательский
процесс не обязан содержать авторизацию или графический интерфейс.

Запрос об ошибке построения, сформулированный как «исправить в правилах/шаблонах,
чтобы другие агенты делали правильно», является задачей развития инструмента.
Сохраняй сформулированное правило здесь и закрепляй его проверкой либо общей
реализацией; не подменяй результат ручным улучшением только одного примера.

## Обязательный порядок: сначала архитектура, затем детали

**Модуль** — часть проекта, которая отвечает за самостоятельную задачу системы и имеет определённый способ взаимодействия с другими частями: вызовы, API, сообщения или события. Для каждого модуля укажи, что он делает, какие данные или команды принимает и какой результат возвращает или публикует. Модуль может включать несколько файлов и классов; наличия отдельного файла, каталога или типа недостаточно для выделения модуля.

Агент обязан:

1. Самостоятельно изучить исходники и определить назначение проекта, его архитектуру и высокоуровневую структуру кода.
2. Зафиксировать высокоуровневое описание: модули, их ответственности, связи и основные сценарии. Для каждого основного сценария указать вход, порядок взаимодействия модулей, передачу управления и данных, результат.
3. Только после этого детализировать диаграмму: добавлять описания, контракты, ссылки на код и конкретные вызовы и так далее.

Выводы подтверждать кодом. Пробелы в понимании обозначать явно; новые факты учитывать в описании архитектуры.

## 1. Подготовь несколько сценариев сразу

Найди самостоятельные операции с разными целями или результатами. У каждой должны быть точка входа, участники и проверяемый исход. Выбирай операции, которые объясняют назначение таргета или важную границу ответственности. Размести их на одной карте. Если узкий таргет действительно участвует только в одном сценарии, покажи его, объясни ограничение и назови ближайший модуль, в котором можно найти другие.

**Как называть.** Используй знакомые владельцу проекта термины. Предпочитай глагол действия и объект, обычно 2–5 слов. В системе заказов подойдут **«Оформить заказ»**, **«Изменить адрес доставки»**, **«Отменить заказ»**. Названия должны различаться без дополнительных пояснений. HTTP-метод, endpoint и имя обработчика вынеси в карточку сценария.

**Что считать развилкой.** «Адрес принят» и «Доставка уже началась» могут быть двумя исходами внутри «Изменить адрес доставки». Помести их в точку выбора этого сценария. Для каждой ветки установи условие и результат по коду.

**Что видно на старте.** Рядом с картой размести открытый список названий. Все подготовленные сценарии доступны сразу, без повторной генерации. По выбору названия покажи точку входа и подсвети маршрут. При переключении поставь воспроизведение на паузу. Сохраняй шаг, историю и выбор веток каждого сценария, чтобы к нему можно было вернуться.

## 2. Построй карту и интерфейс просмотра

### Границы и детализация

Для класса начни с его роли, публичных операций и соседей. Для модуля покажи контракт, компоненты, зависимости и владельца данных. Для репозитория начни с приложений, модулей, хранилищ и точек входа. Для набора репозиториев подпиши межрепозиторные контракты и разреши раскрытие каждого включённого участника. Файлы используй для ссылок на исходники.

### Отбор архитектурных участников и названия

Строй карту ответственностей системы. Список файлов, каталогов, классов, структур и импортов — материал анализа, а не готовый список участников. Перед добавлением узла объясни, какую самостоятельную ответственность он представляет, где проходит её граница и какое реальное взаимодействие или контракт оправдывает её выделение на выбранном уровне. Существование файла, публичного класса или проверяющей функции само по себе этого не доказывает. Одна ответственность может охватывать несколько файлов; несколько вспомогательных функций и типов могут принадлежать одному компоненту.

Конфигурация, YAML/JSON-схема, `Settings`, DTO, параметры, перечисления и пути являются входами, результатами, принадлежащими участнику данными или пояснениями типов. Показывай их в `step.input`/`output`, параметрах контрактов, `ownedData` и `typeExplanations` владельца со ссылками на код. Не делай их отдельными участниками. Наличие чтения/валидации YAML не требует отдельного модуля на карте: если это часть CLI, показывай его внутреннюю операцию. Независимый сервис управления конфигурацией может быть компонентом благодаря своему поведению, API и границе; переименование объекта Settings в «процессор настроек» не создаёт такой границы.

Различай архитектурную абстракцию и её конкретный пример. Для подключаемого семейства алгоритмов показывай точку расширения и общий контракт, например базовые `Strategy` или `JobHandler`, если это их имена в изучаемом коде. Класс демонстрационной реализации, созданный экземпляр и шаблонный файл не становятся самостоятельными компонентами проекта. Их место — пояснение реализации, пример операции или ссылка на исходник. Реальный компонент может быть реализован классом, но выбор обосновывается его ответственностью и взаимодействиями, а не фактом наследования или именем класса. Явно запрошенный разбор конкретного класса/примера имеет более узкую область; это не основание включать все примеры в обзор проекта.

Не добавляй в архитектуру работающего продукта контейнеры «Среда и рабочие каталоги», перечни toolchain/lock-файлов, пустые папки, сборочные рецепты, CI и тестовые фикстуры ради полноты файлового обзора. Нужные версии, команды и расположение файлов сохраняй в метаданных, документации и параметрах соответствующих операций. Архитектура сборки, CI или тестового стенда допустима при отдельно заданной области такой карты. Работающее хранилище с реальным протоколом чтения/записи может быть ресурсом архитектуры; пустой каталог и строка пути сами по себе им не являются.

**Названия из кода.** Модули, компоненты, интерфейсы и другие именованные элементы архитектуры называй так, как они называются в изучаемой версии кода. Используй фактическое имя пакета/crate, модуля, класса, интерфейса или соответствующего каталога; сохраняй регистр, дефисы и подчёркивания. Например, пакет `bcs-client` остаётся `bcs-client`, а класс `InstrumentRegistry` — `InstrumentRegistry`. Не заменяй эти имена переводом, описанием назначения, придуманным общим названием или префиксом «Приложение: …». Ответственность объясняй в `role`, а подробности — в `details` и описаниях контрактов. Совпадающие короткие имена различай по владельцам или точному квалифицированному имени из кода, а не по выдуманным подписям.

Редкое исключение допустимо, если исходное имя слишком сложное для подписи или у ответственности нет применимого имени в коде либо каталоге. В этом случае используй короткое понятное название, укажи исходное имя/состав, если они известны, и причину исключения в подробностях или авторском обосновании. Внешнюю систему без доступного имени в коде называй её установленным именем. Не применяй исключение только ради перевода или одинакового стиля карточек. При обновлении проверь имена всех участников и контрактов по источникам, сохраняя устойчивые ID.

Это правило именования не меняет отбор участников. Нельзя исправить неправильный отбор подписью из кода или более красивым названием: сначала убери артефакт или объедини его с владельцем. Наличие точного имени у Settings, DTO, файла или демонстрационного класса само по себе не делает его компонентом архитектуры.

Проверь весь каталог участников, включая вложенные уровни: для каждого зафиксируй решение оставить, объединить с владельцем, перенести во входы/данные либо исключить из области. Замечания к нескольким примерам требуют пересмотра всего класса ошибок. Сохраняй полезные объяснения и точные источники после объединения. Не сохраняй ошибочный узел ради прежнего ID; устойчивый ID нужен продолжающей существовать ответственности.

`kind` обозначает категорию архитектурного участника. Явные категории данных/артефактов (`config`, `settings`, `schema`, `dto`, `file`, `directory`, `example`, `instance` и подобные) валидатор отклоняет на полотне. Это структурная защита, а не распознавание смысла по названию: `kind: component` не заменяет содержательную проверку отбора. Настоящие компоненты с названиями вроде ConfigService не запрещаются по имени.

Если вызов выходит за пределы выбранных репозиториев, изучи доступные объявления внешнего модуля, класса или сервиса. Покажи карточку **«Внешний API»** с операцией, известными входами, результатом, ошибками и источником. Раскрытие заканчивается на контракте. Если известна лишь клиентская сторона, подпиши «По месту вызова». Для входящего вызова с неизвестным клиентом явно укажи это на границе.

**Масштаб.** Дай приблизить, отдалить и переместить карту. Клик по шапке внутреннего модуля раскрывает его компоненты; повторный клик по шапке сворачивает их, а свободное место внутри остаётся доступным для перетаскивания карты. Перепривяжи стрелки к конкретным участникам взаимодействия. Сохрани путь до модуля, текущий шаг и выбранную ветку при раскрытии и сворачивании. На карточке модуля покажи локальный прогресс, например «пройдено 2 шага». Обновляй его при перемотке и смене ветки.

### Пояснения в карточках

Пиши для разработчика, который знаком с программированием, но ещё не знает выбранный проект. Основное описание роли участника занимает одно, максимум два коротких предложения: что он делает и зачем нужен. Уточнения о взаимодействиях, типах и порядке работы открываются по нажатию на это описание. Каждую существенную связь объясняй действием и его смыслом. Например, «ищет первый ненулевой API» требует пояснения: какие модули перебираются, что у них запрашивается, что означает ненулевой результат, кто считается первым и что происходит, если ничего не найдено.

Имена из кода сохраняй для сопоставления с исходниками и сопровождай объяснением. Тип, сокращение или составная запись вроде `IModule Owner Array` не заменяет описание: объясни, что это за коллекция, какие объекты она хранит, что означает владение и для чего нужен общий интерфейс. Словосочетание «вызывает стадии через IStage» должно раскрывать, что такое стадия, как находятся её обработчики и какой метод вызывается. Не приписывай интерфейсу гарантии, которых нет в объявлениях и реализации.

Раздел с принадлежащим участнику состоянием называй **«Данные во владении»**. Каждый значимый элемент показывай отдельно: имя в коде и короткое объяснение назначения в одном, максимум двух предложениях. По нажатию на этот пункт раскрывай смысл хранимого значения, тип, подробности владения и ссылку на объявление или соответствующий узел карты. Для времени, размера и других величин указывай единицы, когда они известны. Если структура хранит ссылки на чужие данные, поясни это и назови владельца. Перечень имён полей без объяснений недостаточен.

Каждую операцию контракта показывай отдельно, даже если несколько методов принадлежат одному интерфейсу. В кратком представлении рядом с именем операции дай её назначение в одном, максимум двух предложениях. По нажатию на этот пункт раскрывай сигнатуру, пояснения входных аргументов, результат, существенные эффекты и ограничения. Во входах объясняй смысл параметра и типа, допустимое отсутствие значения и единицы измерения, если они применимы. Для структурированного аргумента раскрой значимые поля. Для результата укажи смысл специальных значений: например, нулевого адреса, пустой строки или отсутствующего объекта. Ссылку на подтверждающий код размещай рядом с описываемой операцией.

**Два уровня чтения.** При открытии карточки сначала показывай короткую основную информацию. Подробное объяснение, данные, определения терминов, параметры операций и основания в коде раскрываются по нажатию на соответствующий пункт. Нажиматься должно само краткое описание или его заголовок, а не только маленький значок; повторное нажатие сворачивает подробности. Разреши пользоваться раскрытием с клавиатуры. Ссылки на код внутри подробностей должны открывать источник, не меняя шаг проигрывателя.

Краткий текст должен оставаться понятным без раскрытия: длинное объяснение, механически обрезанное многоточием, или одна сигнатура не заменяют короткого описания. В подробностях сохраняй точность и полезные пояснения предыдущей версии; сокращение исходного экрана не означает удаления этих сведений. Если пунктов много, сгруппируй их в сворачиваемые разделы с понятными названиями и числом элементов.

Применяй этот способ подачи ко всем показанным модулям и их компонентам. Исправление одной образцовой карточки не считается завершённым, если в остальных остаются необъяснённые имена, списки полей или сигнатуры. Проверь краткий и раскрытый вид всего каталога участников, включая внешние API и альтернативные варианты запуска.

### Шаблон вопроса по карточке

В конце карточки каждого шага и каждого участника карты, включая компоненты и внешние API, размести короткий шаблон вопроса и кнопку **«Скопировать»**. Шаблон должен быть доступен без раскрытия остальных подробностей. Покажи его обычным выделяемым текстом, чтобы пользователь мог скопировать его вручную и дописать свой вопрос.

Для шага включи название проекта, зафиксированную ревизию, номер и название сценария, номер шага в текущем выбранном пути и полное название шага. Например: «Помоги разобраться с вопросом по IAD проекта lab-engine: сценарий 4 „Остановить Play“, шаг 3 „Остановить графы до Scene“». Если для однозначного определения пути нужны выбранные ветки, добавь подтверждённые варианты. Предварительный просмотр варианта без подтверждения не меняет контекст шаблона.

Для участника включи название проекта, зафиксированную ревизию, название участника и полный путь к нему от таргета через родительские группы или модули. Такое обращение должно позволять найти карточку без знания того, какой сценарий открыт у пользователя.

Заканчивай шаблон отдельным полем `Вопрос: ` с местом для продолжения. Не подставляй предполагаемый вопрос вместо пользователя. Обновляй контекст при смене сценария, шага, подтверждённой ветки или участника; номера должны совпадать с видимыми номерами в проигрывателе и каталоге.

Копирование переносит только показанный текст в буфер обмена и не отправляет сообщения. Оно не меняет воспроизведение, текущий шаг, решения в развилках и раскрытые подробности. При недоступном буфере обмена сохрани возможность выделить текст вручную и сообщи об этом; подтверждение «Скопировано» показывай только после успешного копирования.

### Визуальная композиция

Сделай интерфейс аккуратным и визуально выразительным. Центральное место отдай карте, список сценариев размести рядом, управление воспроизведением — под картой. Детали шага открывай в боковой панели, сохраняя активный узел в поле зрения. На узком экране панель можно свернуть.

Используй читаемый шрифт, единые отступы и короткие подписи над стрелками. Дай активному маршруту один акцентный цвет, а текущему шагу — заметную обводку и номер. Дублируй смысл цвета подписями или значками. Сохраняй расположение общих узлов при переключении сценариев. Стрелки имеют направление и конкретное действие, например «проверяет адрес», «пишет в БД», «публикует событие». Разводи связи так, чтобы они не перекрывали названия.

**Цветовая тема.** Учитывай предпочтения владельца и используй согласованную палитру во всём интерфейсе: на карте, в списке сценариев, проигрывателе, раскрываемых подробностях, просмотре кода и шаблонах вопросов. Фон, основной текст, второстепенный текст, маршрут, текущий шаг и фокус должны иметь определённые роли; наконечники и маркеры связей должны соответствовать цветам линий. Проверяй контраст текста и различимость состояний на реальном фоне, в том числе на узком экране. Изменение темы сохраняет номера, формы и подписи, позволяющие читать карту без различения цветов.

Для текущей пробной карты `lab-engine` владелец задал и одобрил чёрно-красную основу с небольшими матово-золотистыми акцентами и подходящими дополнительными оттенками. Чёрные фоны должны быть нейтральными, красный — явным и насыщенным: предыдущий вариант был отклонён как коричнево-розовый. Золото не должно тонировать большие поверхности или подменять основной красный акцент. Это настройка оформления данной карты, а не обязательная расцветка формата IAD для всех проектов. При повторном построении сохраняй указанное предпочтение, пока владелец не изменит его; конкретные оттенки и их роли фиксируй в стилях темы.

Оставляй между карточками достаточно свободного пространства для отдельных маршрутов и их подписей. Карточки не должны выглядеть слипшимися; увеличить расстояния в координатах карты недостаточно, если автоматическое уменьшение масштаба снова делает их тесными и нечитаемыми на экране. Проверяй результат при фактическом открытии карты, с открытой панелью и при раскрытии компонентов.

У каждой видимой стрелки должны однозначно читаться исходящий участник, принимающий участник и наконечник. Маршрут не должен проходить через карточку или скрываться за ней так, чтобы создавалось впечатление другого источника связи. Разводи близкие стрелки и их точки подключения; если пути пересекаются или используют общий участок, сохраняй различимость отдельных связей. Подпись должна явно относиться к своей стрелке: не размещай её произвольно в свободном месте вдали от маршрута. Подписи, наконечники и линии не должны перекрывать названия карточек или друг друга так, что связь теряет смысл.

Для связи между соседними компонентами предпочитай компактный маршрут рядом с ними. Нехватка места для длинной подписи не должна превращать локальную связь в большой обход других модулей: используй короткую выноску с явной привязкой к линии. Начало исходящей связи должно отличаться от её конца; наконечник обозначает получателя. Дополнительные маркеры начала объясняй в легенде. При автоматическом кадрировании текущего перехода держи источник и получателя в поле зрения, если оба помещаются в доступную область при выбранном читаемом масштабе. Проверяй такие связи после раскрытия вложенных компонентов и при смене текущего шага: пройденная связь должна оставаться читаемой, даже если приоритет подсветки перешёл к другой.

Для многострочной подписи оценивай близость всего текстового блока к собственной стрелке, а не расстояние до первой строки. Подпись над горизонтальным сегментом может оставаться рядом с ним нижней строкой; это не повод считать её оторванной или требовать лишнюю выноску. Удалённый от линии блок по-прежнему требует явной привязки.

### Источники данных и API карты

Для связи или шага укажи репозиторий, точный коммит, путь и символ либо ссылку на трассировку. Импорт подтверждает зависимость на уровне кода. Чтобы показать передачу управления, найди вызов, регистрацию обработчика или трассу. Неподтверждённый переход пометь явно.

**Просмотр исходников — обязательная часть IAD.** Сохраняй доступ к подтверждающему коду из карточек участников и шагов, описаний данных и отдельных операций. В кратком виде карточки достаточно указателя на подробности; внутри подробностей размещай понятные ссылки или кнопки с путём файла, строкой и именем символа. Если утверждение опирается на несколько мест, предоставь каждое из них.

По нажатию открывай встроенный просмотр кода поверх карты или рядом с ней. Сначала показывай фрагмент вокруг нужной строки с достаточным контекстом для чтения вызова или объявления. Нумерация должна соответствовать исходному файлу; целевую строку выделяй. Дай раскрыть весь файл и перейти к той же строке. Показывай исходный текст, сохраняя отступы и порядок строк.

В заголовке просмотра явно указывай репозиторий, полный SHA коммита, путь файла, номер строки и имя символа. Короткий SHA допустим в обзорной части интерфейса, если полный доступен в просмотре источника и манифесте. Для внешнего API указывай его собственный репозиторий и проверенную ревизию зависимости, а не коммит основного проекта.

Если у репозитория настроен серверный адрес, из встроенного просмотра дай явный переход к этому файлу, на тот же коммит и нужную строку. Для локального репозитория без сервера не выдумывай URL: показывай отсутствие серверной ссылки, сохраняя полный локальный снимок и метаданные. Такая ссылка одновременно открывает исходный файл и его контекст в репозитории; открывай её в отдельной вкладке, сохраняя доступ к карте. Привязывай ссылку к точной ревизии, а не к подвижной ветке или текущему HEAD. Текст в локальном просмотре и файл по серверной ссылке должны соответствовать одной версии.

Включай в поставку точные снимки используемых исходных файлов, чтобы встроенный просмотр фрагментов и полных файлов работал без сети. Сохраняй для снимка репозиторий, полный коммит, путь и контрольную сумму содержимого; для каждого подтверждения — ссылку на снимок, строку, символ и, при настроенном сервере, адрес файла в репозитории. Сверяй содержимое с указанной ревизией. Если исходник недоступен, явно обозначай отсутствие локального просмотра; недоступный текст нельзя выдавать за проверенное подтверждение.

При открытии и закрытии источника, а также раскрытии полного файла сохраняй выбранный сценарий, решения, раскрытые модули и установленный режим воспроизведения. Сам переход к коду не перематывает сценарий. Проверяй сохранение текущего шага при поставленном на паузу проигрывателе: пользователь должен вернуться к тому же месту карты.

В манифесте зафиксируй таргет, ревизии репозиториев и значимые настройки. В модели карты сохрани узлы, связи, контракты, сценарии, развилки и проверенные пояснения. Используй устойчивые идентификаторы для сравнения версий.

Предоставь API для получения каталога сценариев, дочерних узлов, связей, шагов и вариантов, а также для построения и сравнения снимков. Опиши вход, результат и ошибки операций. Для неоднозначного имени таргета верни список кандидатов.

## 3. Реализуй проигрыватель сценариев

- **Пуск и пауза.** Автовоспроизведение последовательно подсвечивает шаг, модуль и переход к следующему участнику. Пауза останавливает его на текущем шаге и оставляет его описание открытым. Дай изменить скорость и запустить сценарий с начала.
- **Шаг назад и шаг вперёд.** Один клик перемещает на один шаг выбранного пути. Повторный заход в тот же модуль занимает отдельное место в истории. Раскрытие узла меняет детализацию карты, сохраняя позицию проигрывателя.
- **Перемотка.** Добавь шкалу шагов с перетаскиваемым указателем и переходом по клику. Перемотка назад или вперёд ставит показ на паузу и синхронно меняет подсветку, панель и прогресс. При движении вперёд остановись на первой развилке, где пользователь ещё не выбрал вариант.
- **Выбор ветки.** На развилке останови автопоказ и покажи варианты. Клик по варианту открывает условие, последствие и следующий шаг. Пользователь может изучить все варианты. Только кнопка **«Выбрать и продолжить»** фиксирует решение и открывает первый шаг ветки. Если пользователь вернулся и сменил решение, замени прежнее продолжение истории.
- **Информация о шаге.** Покажи, кто передал управление, кто его получил, какие данные поступили, что сделал модуль и что получилось. Отдельно отметь существенный нюанс, например границу транзакции, ошибку, повтор или фоновую обработку. Дай ссылку на код либо трассу. Для HTTP явно обозначь шаг ответа клиенту.

### Как проверить поведение на запросе

Иллюстративный пример — «Изменить адрес доставки». На входе виден PUT-запрос на изменение адреса. Проигрыватель доходит до проверки статуса доставки и встаёт на паузу. Пользователь открывает вариант «Доставка уже началась» и читает причину отказа. Пока выбор не подтверждён, на карте остаётся подсвеченной проверка. Затем пользователь подтверждает отказ, видит ответ клиенту, возвращается на проверку и проходит другую ветку.

В поставке используй реальные операции и исходы выбранного проекта. Различай маршрут **«По коду»** и запись **«По трассировке»** со ссылкой на запуск. Переход к альтернативной ветке записи явно обозначай как симуляцию. Для параллельных действий показывай только известные ограничения порядка. Все кнопки проигрывателя управляют локальным просмотром.

## 4. Покажи изменения и сдай результат

**Режим сравнения.** Зафиксируй версии «до» и «после» для каждого репозитория. Для обычного коммита возьми за базу его родителя, для первого — пустое дерево, для merge-коммита явно укажи родителя. Открой затронутый участок карты и перечисли сценарии, на которые повлияло изменение. Покажи добавление, удаление или изменение контракта, зависимости, владельца данных, условия ветвления либо гарантии. Дай последствие для клиента или соседнего модуля и ссылки на основания в соответствующих версиях.

Для сравнения двух подготовленных моделей используй общий экран с картами «До» и «После»: дай исследовать один и тот же сценарий в каждой версии и перейти к первому расхождению. Например, клиент раньше получал подтверждение после записи, а теперь получает его после постановки задачи в очередь. Подсвети перенос момента подтверждения, даже если состав модулей прежний. Предлагаемое изменение ответственности, контракта или гарантии вынеси владельцу на решение до реализации в изучаемом проекте.

### Критерии приёмки

1. **Первое открытие.** На таргете с несколькими операциями названия разных сценариев видны сразу. По каждому названию понятно, какое действие будет показано. Два сценария открываются на одной карте и сохраняют свой прогресс при переключении.
2. **Карта и границы.** Раскрой модуль во время паузы и вернись на уровень выше. Активный шаг и ветка сохранились. У внешнего участника открывается карточка контракта. Внутреннюю структуру можно исследовать после явного включения его репозитория.
3. **Проигрыватель.** Проверь пуск, паузу, скорость, шаги назад и вперёд и перемотку в обе стороны. На невыбранной развилке автопоказ и перемотка останавливаются. Просмотр двух вариантов сохраняет позицию. Подтверждение и последующая смена ветки обновляют маршрут, панель деталей и счётчик.
4. **Читаемость.** На обзорном и вложенном уровнях видны названия, направление стрелок и текущий шаг. При открытой панели активный узел остаётся в поле зрения. Состояние можно определить по форме, номеру или подписи даже без цвета.
5. **Проверяемость.** Из шага можно открыть подтверждение в выбранной ревизии. Для того же таргета, версий и настроек воспроизводятся те же сценарии, связи и ветки. В режиме сравнения показано первое подтверждённое расхождение либо явно сообщено, что сравниваемые сценарии совпадают.
6. **Понятность и объём описаний.** В каждой карточке основная роль изложена в одном, максимум двух коротких предложениях. По нажатию открываются подробности; данные, термины и операции используют такой же принцип краткого объяснения с раскрытием. Разработчик без знания проекта может понять роль по краткому виду, а по подробному — значение данных, входных параметров и специальных результатов. Ссылки связывают имена с кодом. Проверка охватывает все модули и компоненты, а не только одну образцовую карточку.
7. **Стрелки и расстояния.** В обзорном и раскрытом состоянии можно проследить каждую показанную связь от её источника до наконечника и сопоставить с подписью. Карточки оставляют место для чтения маршрутов; подписи не перекрывают названия и не оторваны от стрелок. Связь соседних вложенных компонентов остаётся локальной; её направление и подпись понятны до и после перехода к следующему шагу. Проверка проводится в браузере при используемом начальном масштабе и после изменения масштаба.
8. **Шаблон вопроса.** В конце каждого шага и участника можно скопировать готовое обращение, дописать вопрос и по вставленному тексту однозначно найти нужную карточку и версию. После перемотки и смены ветки номера и названия шага соответствуют текущему пути; просмотр неподтверждённого варианта их не меняет. Кнопка копирования не меняет состояние просмотра, а при недоступном буфере текст можно выделить вручную.

9. **Просмотр и происхождение кода.** Открой источник из шага, участника, поля данных и операции. Встроенный просмотр показывает фрагмент с исходными номерами строк и выделенной целевой строкой, репозиторий, полный коммит, путь и символ. Раскрой весь файл и проверь переход к той же строке. При настроенном сервере ссылка на репозиторий ведёт к этому файлу и строке в той же ревизии; у локального проекта отсутствие URL обозначено явно. При отключённой сети локальный код остаётся доступен. После закрытия просмотра на паузе сохраняются шаг, ветка и раскрытие карты.

**Передай владельцу** открываемую HTML/JS-диаграмму, манифест, модель карты, снимки использованных исходников и результат проверок. Если заданы две версии, добавь вход в демонстрацию коммита. В сопроводительной записке укажи, какой сценарий открыть первым и где остались неподтверждённые связи.

## 5. Используй каркас и канонические данные

Внешний каталог данных диаграммы содержит `project.json`, необязательный `view.json` и категории `nodes`,
`edges`, `contracts`, `scenarios`, `evidence`. Каждая категория состоит из JSON-файлов
с одной сущностью либо массивом. Схемы находятся в `iadkit/schemas/` и задают
машинный контракт версии 1. Подробности заполнения находятся в `docs/authoring.md`,
справочник полей — в `docs/format.md`; требования к смыслу и поведению задаёт этот документ.

Название проекта, репозитории, начальный сценарий, порядок карточек, интервалы и
цветовые настройки должны задаваться данными. Для новой карты не меняй HTML,
JavaScript и CSS ядра. Не добавляй в общий сборщик знание конкретных имён модулей,
языка, файлов зависимостей или порядка стадий. Извлечение проектных фактов выполняет
отдельный адаптер либо агент. Адаптер выдаёт тот же канонический формат.

Изменяй авторские JSON, затем запускай `validate` и `build`. HTML, собранная модель,
манифест и архив источников создаются автоматически. Ручная правка результата
сборки не считается обновлением проекта: при повторной сборке она исчезнет.
Сохраняй устойчивые ID при переименовании понятной человеку подписи.

**Происхождение кода и истинность вывода — разные проверки.** Сборщик вычисляет
`sourceIntegrity`: `git-verified` означает чтение точного Git blob,
`archive-verified` — проверку идентичности и SHA-256 архивного текста при отсутствии
доступного checkout. Архив без сверки с Git не доказывает происхождение из коммита.
Недоступный текст вызывает ошибку. Рабочее дерево не подменяет зафиксированную версию.

Автор указывает `support.kind`: `declaration` для объявления, `implementation`
для проверки условия, присваивания или возврата в теле реализации, `callsite`
для места вызова, `registration` для регистрации, `trace` для связанной записи
исполнения, `reference` для общего указателя. `support.status` показывает, проверено
ли это основание; `verification.status` у шага или связи показывает проверенность
самого утверждения. Допустимы `reviewed`, `unreviewed`, `uncertain`. Не присваивай
`reviewed` автоматически по факту существования файла или прохождения схемы.
Для вызова нужны подходящие основания передачи управления. Статус автора не является
автоматическим доказательством — валидатор проверяет согласованность данных, а не смысл кода.

При импорте старого формата не переименовывай технический `confirmed` в семантический
`reviewed` без повторного чтения соответствующего кода. Сохрани описание, источник и
пометку о необходимости проверки. Предупреждения допустимы для черновой карты и
должны быть видимы в отчёте и подробностях; ошибки ссылок, циклы маршрута, неверные
ревизии и повреждённые исходники блокируют сборку. Строгая проверка также отклоняет
предупреждения. При ошибке не выдавай оставшийся старый HTML за новый успешный результат.

Манифест должен фиксировать версию формата и каркаса, таргет, точные версии всех
репозиториев, значимые настройки и контрольные суммы авторских входов, общего ядра,
схем и этих правил. Сборка одинаковых входов при одинаковой доступности Git/архивов
должна давать одинаковые байты без текущего времени. Изменение способа проверки
источника с архива на Git явно меняет его статус происхождения.

Проверяй каркас на моделях разной структуры, собранных одним ядром без
проектных правок JavaScript. Тестовые модели создавай во временном каталоге;
проверку реальных проектов выполняй отдельно во внешнем каталоге данных. Один пример должен содержать несколько сценариев и
развилку. Кроме структурных проверок используй проверки проигрывателя, геометрии
стрелок и браузерных действий; ясность текста и соответствие коду проверяй отдельно.

## 6. Сохраняй обратную связь

После изменения требований обновляй этот документ точными проверяемыми правилами.
Записывай исправления и положительную обратную связь: одобренные возможности
должны воспроизводиться при следующих построениях. Не заменяй конкретное наблюдение

## 8. Строй сравнение на двух проверяемых версиях

Для диаграммы изменений подготовь две обычные IAD-модели в `before/` и `after/`
внутри отдельного каталога диаграммы. Обе модели должны иметь один таргет и
устойчивые ID общих участников и сценариев. Каждая модель описывает действия
только своей ревизии и содержит собственные точные источники.

Сводку в `comparison.json` составляй по коду: изменение, его последствие, связанный
сценарий, источники до и после, участники для фокуса. Экран сравнения должен явно
показывать обе ревизии, позволять переключить карты, открыть основания каждой
стороны и перейти к соответствующим шагам первого расхождения. Сохраняй возможность
изучать ветки и полные исходники каждой стороны без сети.

Для неизменившихся фактов сохраняй одинаковые тексты: формальный алгоритм сравнения
учитывает формулировки. Первое расхождение модели не является автоматическим
доказательством изменения программы; проверь смысл и последствия по обеим версиям.
В результатах сравнения храни выбранные ветки структурой `choices`, пригодной
для воспроизведения пути. Ссылки на старый код должны сохранять старую ревизию.

Если изменение объединяет модули или переносит состояние, покажи старого и нового
владельца и соответствующий маршрут. Различай изменение внутренней ответственности,
изменение контракта и видимый для клиента исход. Для каждой заявленной гарантии
предоставь подходящее основание. Поддержка двух авторских моделей не означает
автоматическое извлечение архитектуры произвольного коммита.


## 9. Согласуй уровень карты, вложенность и сценарии

Для набора репозиториев начни с равноправных контейнеров систем. Внутренние модули
каждого репозитория размещай под его контейнером. Например, клиентское приложение,
API-сервис и вычислительная библиотека находятся на одном уровне; обработчики,
планировщик и хранилище библиотеки — внутри её контейнера.
У контейнера задай `kind: repository` и `repository` с ID выбранной версии. Внешние
участники могут находиться на границе, если их назначение явно обозначено. Владение
узлом определяй по ответственности и иерархии; ссылка на чужой исходник не переносит
клиента в другой репозиторий. Контракт иной закреплённой версии сохраняй отдельной границей.

Раскрытие должно существенно расширять границы контейнера и показывать внутри такую
же двумерную архитектурную диаграмму: обычные читаемые карточки, связи, направления,
подписи и возможность дальнейшего раскрытия. Небольшую группу с простыми связями
располагай вертикально и плотнее; число колонок не является признаком полноценной
диаграммы. Для сложных сетей сохраняй несколько колонок и место для маршрутов.
Список в информационной панели — вспомогательная
навигация. Внутренние стрелки и подписи принадлежат своей области; пути между системами
сохраняют понятные пересечения их границ и обходят чужие раскрытые области.

У каждого сценария указывай `scope` — область каталога, и `trigger` — фактическое
начальное действие. На обзоре платформы прежде всего показывай внешние цели, соответствующие её
назначению: действия UI, запросы API, команды CLI, обработку событий либо операции
библиотеки. Авторизация и облачные проекты уместны только при наличии в исходном коде. От
обработчика кнопки проследи UI, запрос, обработку и ответ либо явно обозначенную границу
внешнего кода. Native/web и другие варианты различай по фактической реализации.
Кадр, стадии runtime, тики, GPU-очереди и фоновые worker/cleanup процессы изучаются
внутри соответствующего репозитория или модуля. Для намеренно обзорного системного
процесса укажи `overviewReason`. Классификацию определяет смысл, а не ключевое слово.

Контекст каталога меняется явным действием навигации. Автоматическое раскрытие узлов
при проигрывании не меняет список сценариев. При раскрытии сохраняй выбранный путь,
позицию и решения. Обзор показывает обзорные сценарии; внутри области доступны её
собственные, дочерние и относящиеся к ней родительские маршруты. `scope` не является
ограничением на участников: сквозные сценарии обращаются к узлам разных репозиториев.

Полноту проверяй по точкам входа, ответственностям, данным, контрактам, пользовательским
действиям и взаимодействиям. Уже описанные модули могут казаться пустыми из-за неверной
визуализации; проверь и данные, и представление. У небольшого backend может быть меньше
узлов, чем у engine: произвольная квота или равное число карточек не заменяют анализ.
Назови границы охвата и проверь внутренние связи; записи о компонентах без отношений
между ними недостаточно для интерактивного изучения архитектуры.

## 10. Управляй контейнерами, плотностью и точками API предсказуемо

Раскрывай и сворачивай модуль нажатием на его **шапку**. Шапка должна иметь
понятный индикатор состояния и работать с клавиатуры. Внутри раскрытой области
свободное место принадлежит полотну: зажатая основная кнопка мыши и перемещение
панорамируют карту, не закрывая модуль. Нажатие на пустое место не сворачивает его.
Дочерняя карточка и её шапка управляют только дочерним участником; события не должны
сворачивать родителя. Нажатие на порт API, стрелку или ссылку также не меняет
раскрытие контейнеров. Панорамирование сохраняет шаг, ветки и выбранный уровень.

Подбирай раскладку по сложности связей. Если участников немного и зависимости
образуют простую цепочку, используй компактное вертикальное
расположение. Это относится и к обзору, и к внутренней диаграмме. Плотность не
должна скрывать наконечники, подписи и доступные для нажатия интерфейсы. Сложные
сети и крупные раскрытые соседи требуют двумерных проходов. Явно заданную автором
раскладку сохраняй; автоматический выбор зависит от полной структуры модели,
а не от текущего шага или режима показа связей.

У каждой карточки компонента и контейнера обозначай **точки подключения** на
контуре — например, короткими утолщёнными отрезками. Стрелка должна начинаться
и заканчиваться в обозначенной точке, а не в произвольном месте рамки. Один
объявленный контракт имеет устойчивую идентичность: связи к нему не должны
создавать видимость нескольких разных API. Различай предоставляемый интерфейс,
использование чужого интерфейса и обычную связь, для которой API ещё не описан.
Не придумывай методы или публичные интерфейсы по одному наличию стрелки.

Для крупного модуля показывай его внешние интерфейсы на внешней границе и после
раскрытия. Контракт скрытого компонента можно спроецировать на видимую границу
владельца, сохранив имя настоящего предоставляющего компонента и путь к нему.
Внутренние связи остаются внутри общего контейнера; линии между системами обходят
посторонние раскрытые области. Цвет, форма, подпись и фокус должны позволять
найти интерфейс и сопоставить его со стрелкой.

На обзоре систем связывай контейнеры через их фактические внешние контракты;
подробные вызовы внутренних компонентов изучаются в соответствующих сценариях.
Явная ссылка на API контейнера привязывает стрелку к его границе даже при
раскрытых компонентах. Сохраняй исходных участников в описании использования.
Контракт общего предка в списке контекста не означает, что оба конца внутренней
связи являются API этого предка; неоднозначность требует явной привязки.

Точка API нажимается мышью и с клавиатуры. По нажатию покажи краткое назначение,
предоставляющего участника, потребителей и направление использования, операции,
входы, результаты, ограничения и основания в коде в пределах имеющихся данных.
Подробности методов раскрывай по общему правилу краткого и полного чтения.
Если контракт не установлен по коду, явно назови точку обычной связью и сохрани
известное описание отношения вместо выдуманной спецификации API. Просмотр порта
не перематывает сценарий, не меняет решения и не сворачивает модули.

Проверь в браузере: перетаскивание из свободного места раскрытого контейнера,
сворачивание только его шапкой, независимое раскрытие ребёнка, компактную простую
цепочку и сложную сеть, API листового компонента и раскрытого крупного модуля,
клик и Enter/Space на точке подключения, источники и сохранение прогресса.

## Надёжность сборки и просмотра

Сборка не должна перезаписывать авторские входы, включая архив исходников и файл
правил. Проверяй совпадение всех выходных файлов с входами до записи результата,
в том числе через символические и жёсткие ссылки. Манифест должен содержать хэши
всех принятых входов под логическими относительными именами, даже когда JSON
прочитан через внешнюю символическую ссылку.

Отклоняй повторяющиеся ключи JSON, неконечные числа и числовое переполнение при
чтении проекта, сравнения и архива. Проверка и сборка должны одинаково отвергать
такие данные с указанием входного файла.

Нумерация исходников в проверке, ссылках и просмотрщике должна использовать LF;
Unicode-разделители и form-feed внутри текста не считаются отдельными строками,
а завершающий LF не добавляет пустую строку.

Начальная область должна раскрываться при первом открытии вместе с родителями
участников начального шага. Сходящиеся ветки допустимы: просмотр и сравнение
