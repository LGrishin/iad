# Заполнение заготовки

Этот каталог содержит пустые авторские данные. `init` заполняет только имя,
исходный репозиторий и закреплённую версию. Анализ архитектуры выполняет агент.

1. Прочитай `START.md`, `AGENTS.md`, `iadkit/spec/iad-rules.md` и `docs/hierarchy.md`
   в репозитории каркаса. Учитывай инструкции исходных репозиториев.
2. Зафиксируй область карты и версии всех исходных репозиториев.
3. Самостоятельно изучи исходники, назначение проекта и структуру кода.
4. Зафиксируй высокоуровневое описание: модули, ответственности, связи,
   основные сценарии с передачей управления и данных от входа до результата.
   Модуль — часть проекта с самостоятельной задачей и определённым способом
   взаимодействия с другими частями. Укажи, что он делает, что принимает
   и какой результат выдаёт. Он может включать несколько файлов и классов.
   Только после этого добавляй подробные описания, контракты, ссылки на код
   и вызовы. Выводы подтверждай кодом; новые факты учитывай в общей модели.
   Определи уровни архитектуры. Для нескольких репозиториев создай равноправные
   контейнеры, внутренние модули — внутри владельцев.
   Перед созданием узлов проверь для каждого кандидата ответственность, границу и взаимодействие. Конфиги, Settings, схемы, DTO, пути и примеры перенеси во входы/данные/пояснения владельца. Показывай общий контракт расширения вместо конкретной демонстрационной реализации. Не добавляй окружение, папки, сборку, CI и тестовые фикстуры в runtime-карту без отдельно заданной области.
5. Заполни `nodes/`, `edges/`, `contracts/`, `scenarios/`, `evidence/` по фактическому
   коду. Названия участников и интерфейсов бери из кода или каталогов, сохраняя регистр, дефисы и подчёркивания. Назначение объясняй в роли, а не вместо имени. Исключение допустимо редко: исходное имя слишком сложное либо подходящего имени нет; укажи причину и оригинал, если он известен. Роль — 1–2 коротких предложения, подробности — в отдельных полях. Повторно проверь весь каталог узлов, включая вложенные; имя из кода не делает артефакт компонентом.
6. Укажи `scope` и фактический `trigger` сценариев. Входы выбирай по назначению
   проекта: действия UI, запросы API, команды CLI, события или операции библиотеки.
7. Свяжи вызовы с фактическими контрактами предоставляющих компонентов. Не придумывай
   API по наличию связи; для неустановленного контракта сохрани честное описание отношения.
   Интерфейсы отображаются на контуре компонентов и крупных контейнеров.
8. Настрой `view.json`, выполни `validate`, исправь ошибки и выполни `build`.
   Осмотри вложенные диаграммы и сценарии в браузере. Назови неопределённости.

Проверь панорамирование из пустого места раскрытого модуля и сворачивание только
по его шапке, компактное вертикальное расположение простых групп и нажатие на API
с просмотром операций и исходников. Эти действия сохраняют прогресс сценария.

Команды выполняются из каталога каркаса с путём к этому внешнему каталогу данных.
После заполнения результат появляется в `build/index.html`. Повторные изменения
вносятся в авторские JSON; общий просмотрщик берётся из каркаса.

Пустая заготовка намеренно не проходит проверку полноценной диаграммы.
