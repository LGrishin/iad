# Диаграмма архитектурных изменений

Сравнение состоит из двух обычных IAD-проектов и общего `comparison.json`.
Каждая сторона имеет собственные закреплённые версии, проверенные основания и
полные снимки исходников. Обе карты используют общий просмотрщик IAD Kit.
Они создаются по отдельному запросу во внешнем каталоге. В самом каркасе нет
готовой пары версий или данных конкретного проекта.

Папку для сравнения можно указать в запросе. Если путь не указан, агент выбирает
подходящий каталог вне IAD Kit и сообщает его в результате; фиксированного пути
по умолчанию нет. Ниже `<diagram-dir>` обозначает выбранный каталог.

```text
<diagram-dir>/
  comparison.json
  before/
    project.json
    view.json
    nodes/ edges/ contracts/ scenarios/ evidence/
  after/
    project.json
    view.json
    nodes/ edges/ contracts/ scenarios/ evidence/
  build/
    index.html
    before/
    after/
```

Запуск из каталога каркаса:

```sh
python3 -m iadkit compare "<diagram-dir>"
python3 -m http.server 8011 --bind 127.0.0.1 --directory "<diagram-dir>/build"
```

Открой `http://127.0.0.1:8011/` либо готовый `build/index.html` напрямую в Chrome.
Общий HTML включает обе карты и их исходники через `iframe.srcdoc`; сеть не требуется.
`compare` принимает `--strict`, `--repo ID=PATH` и `-o OUTPUT`.

## Что заполняет агент

1. Выбери содержательное изменение и границы карты. Для обычного коммита используй
   первого родителя и сам коммит; для merge явно назови выбранного родителя.
   Зафиксируй полные SHA всех участвующих репозиториев в каждой стороне.
2. Прочитай обе версии и создай две канонические модели. Сохраняй ID для тех же
   участников, контрактов и шагов; изменившееся размещение или ответственность
   отражай полями. Переименованные символы можно связывать устойчивым ID, пояснив
   старое и новое имя. Вне выбранной области перечисли ограничения.
3. Для неизменившегося поведения используй одинаковые формулировки. Сравнение
   моделей учитывает текст: стилистическая правка тоже будет отличием. Отдельно
   проверь, какое наблюдение стоит за каждым значимым изменением.
4. Заполни сводку изменений: что изменилось, последствие для клиента/соседнего
   модуля, связанный сценарий и основания каждой стороны. Краткий текст — 1–2
   предложения; подробности можно раскрыть. Для источников используй ID оснований
   из соответствующей модели, для фокуса — её ID участников.
5. Выполни `compare`, проверь вкладки версий, сценарии, первое расхождение и код
   обеих ревизий без сети. Ошибки и неизвестные участки должны быть отражены явно.

Схематический пример `comparison.json`; ID сценария, узлов и оснований должны
существовать в соответствующих заполненных моделях:

```json
{
  "schemaVersion": 1,
  "id": "request-refactor",
  "title": "Как изменилась обработка запросов",
  "summary": "Координация обработки перенесена в отдельный модуль.",
  "before": "before",
  "after": "after",
  "changes": [
    {
      "id": "request-coordinator",
      "title": "Отдельный координатор обработки",
      "summary": "Обработчик передаёт подготовку и выполнение координатору.",
      "consequence": "Обработчик отвечает за входной запрос и преобразование ответа.",
      "scenarioId": "submit-request",
      "beforeSources": ["request-handler"],
      "afterSources": ["request-dispatch"],
      "beforeNodes": ["handler"],
      "afterNodes": ["coordinator"]
    }
  ]
}
```

## Первое расхождение

Экран сравнения использует `IADCore.compareSnapshots`. Он обходит шаги и варианты
в порядке моделей, учитывает явно используемые контракты и возвращает первое
отличие выбранного сценария. При вставке или удалении линейного шага фокусом
становится первое различающееся действие; изменение `next` у его неизменившегося
предшественника остаётся в перечне изменений модели. Это порядок изучения веток, а не временная
последовательность альтернативных исходов. Для перехода сохраняются структурированные
решения `choices`, поэтому составные идентификаторы шагов остаются однозначными.
Контракты учитываются через `contracts`, `sourceContract` и `targetContract`.
Сходящиеся ветки не требуют разворачивать общий хвост для каждого пути;
порядок поиска расхождения сохраняется. Для позиции обхода больше
`Number.MAX_SAFE_INTEGER` поле `ordinal` возвращает точную десятичную строку.

По нажатию оба просмотрщика переходят к соответствующим шагам со своими
подтверждёнными ветками. Их источники открываются в собственных точных ревизиях.
Самостоятельное проигрывание каждой карты остаётся локальным просмотром.

Сборщик сравнения работает с подготовленными авторскими моделями. Автоматический
анализ произвольного Git diff и получение архитектурных выводов из него требуют
анализа агентом или отдельного адаптера. Совпадение моделей не доказывает
эквивалентность непредставленного кода.
