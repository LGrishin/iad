# Уровни архитектуры и вложенные диаграммы

На обзоре набора репозиториев показывай равноправные контейнеры репозиториев.
Внутренние модули каждого находятся под своим владельцем. Например, обработчик
запросов репозитория A и очередь задач репозитория B не становятся соседями
корневых контейнеров. Внешние пользователи и системы могут располагаться рядом
с репозиториями, если их роль на границе явно обозначена.

Изучи исходники и назначение проекта. До детализации зафиксируй модули,
их ответственности, связи и основные сценарии от входа до результата.
Затем раскрывай уровни архитектуры и добавляй подробности, источники и вызовы.

Число узлов не заменяет анализ: крупный включённый репозиторий должен раскрываться
до своих основных модулей, их состояния, контрактов и взаимодействий.

На каждом уровне остаются архитектурные ответственности. Вложенность не превращает конфиг, DTO, пример стратегии, экземпляр класса или перечень каталогов в компонент. Не создавай служебный контейнер, чтобы разместить такие сущности на полотне: перенеси их во входы, данные, пояснения и источники владельца. Для подключаемых реализаций показывай общий контракт расширения. CI, сборка и тестовое окружение требуют собственной явно выбранной области, а не добавляются к runtime-карте продукта из-за наличия соответствующих файлов.

Имена на каждом уровне совпадают с именами пакетов, модулей, классов,
интерфейсов или каталогов исходного проекта. Роль контейнера объясняется
отдельно. Одинаковые имена дочерних компонентов различаются по владельцам;
при необходимости используй точное квалифицированное имя из кода. Для редкого
исключения из-за сложного или отсутствующего имени сохрани обоснование
и известное исходное имя в подробностях.

## Авторские данные

Схематический фрагмент узла контейнера:

```json
{
  "id": "repo-a",
  "label": "Repository A",
  "kind": "repository",
  "repository": "source-a",
  "role": "Принимает запросы и передаёт задачи исполнителям.",
  "sources": ["request-entry"]
}
```

Внутренний модуль задаёт `parent: "repo-a"`; его компоненты указывают своим
родителем этот модуль. `repository` — ID из `project.json.repositories`;
поле наследуется по родителям. Оно описывает принадлежность, а не выводится
из `sources`: клиент может ссылаться на объявление чужого API.

Внешний контракт внутри репозитория можно связать с отдельно закреплённой
исключённой зависимостью. Проверяй её точную версию: один клиент может использовать
ревизию зависимости, отличающуюся от версии её самостоятельной карты.

Для `target.type: "repository-set"` валидатор требует корневые контейнеры
включённых репозиториев и размещение внутренних модулей в их границах.
Он предупреждает о контейнерах без компонентов, внутренних связей или локальных
сценариев. Автор отдельно проверяет содержательную полноту и записывает ограничения.

## Сценарии соответствуют назначению и уровню

У сценария `scope` содержит ID области карты или `null` для обзора.
`trigger` описывает фактический вход: `user`, `system`, `developer`, `internal`;
`label` объясняет событие, `sources` указывает его место в коде. Фрагмент сценария:

```json
{
  "scope": null,
  "trigger": {
    "kind": "user",
    "label": "Отправить запрос из формы",
    "sources": ["submit-handler"]
  }
}
```

Это иллюстрация отдельных полей, а не готовая диаграмма: участники, основания,
цель и шаги определяются изучаемым проектом.

Обзор отвечает на вопросы о назначении таргета. Для приложения проследи значимые
действия пользователя; для API — входящие запросы и ответы; для CLI — команды
и результаты; для библиотеки — публичные операции и взаимодействия клиента.
Выбирай реальные точки входа по коду и называй фактического инициатора.
Авторизация, рендеринг и любые другие предметные сценарии появляются только
там, где они объясняют выбранный проект.

Например, при разборе UI-действия проследи обработчик, изменения состояния,
внешний запрос, доступную серверную обработку, ответ и отображение результата.
Если управление уходит в недоступный внешний компонент, закончи известный путь
на контракте и обозначь границу. Для API, CLI и библиотек используй соответствующую
цепочку вызовов; интерфейс пользователя не требуется придумывать.
Различай варианты конфигурации, если их поведение отличается.

Внутренние циклы, обработка очереди и фоновые задачи имеют собственные области
внутри владельцев. Обзорный системный процесс допустим, когда он важен для
назначения таргета; объясни выбор в `overviewReason`. Название операции само по
себе не определяет её уровень: учитывай роль в выбранной системе.

`scope` задаёт каталог сценариев и не ограничивает участников маршрута.
Внутренний сценарий может обращаться к внешнему API; сквозной сценарий — включать
глубокие узлы нескольких репозиториев.

## Просмотр

Нажатие на шапку контейнера существенно увеличивает его границы и раскрывает внутри
архитектурную диаграмму; повторное нажатие шапки сворачивает её. Пустое место внутри
раскрытого контейнера служит для перетаскивания полотна и не закрывает модуль.
Действие дочерней карточки, порта API или стрелки не сворачивает родителя.
Вложенные участники используют обычные читаемые карточки,
связи, подписи, инспектор и ссылки на код. Список компонентов в панели подробностей
служит дополнительной навигацией; он не заменяет внутреннюю диаграмму.

Небольшие группы с простыми цепочками автоматически размещаются
вертикально и компактнее. Сложные сети сохраняют двумерную раскладку и проходы
для связей. Автоматический выбор учитывает полную модель, а не выбранный сценарий;
явные настройки расположения имеют приоритет. Карточки сохраняют читаемый размер.

У компонентов и больших контейнеров точки подключения обозначены на контуре.
Связи к API входят в соответствующий интерфейс; его маркер открывает предоставляющего
участника, потребителей, операции и источники. Внешние API остаются на границе
раскрытого контейнера. При проекции контракта скрытого ребёнка показывается его
настоящий владелец. Неописанный контракт не заменяется выдуманным API: маркер
обычной связи показывает только известные отношения.

Каталог учитывает выбранный уровень: в обзоре видны обзорные сценарии; внутри
контейнера — его собственные, дочерние и относящиеся к нему родительские маршруты.
Кнопки «Обзор» и «На уровень выше» явно меняют контекст. Проигрывание и автоматическое
раскрытие участников не переключают уровень каталога. Раскрытие сохраняет текущий
шаг, подтверждённые решения и локальный прогресс.

Внутренние стрелки и подписи остаются в общей области участников. Маршруты обходят
чужие раскрытые контейнеры. Если построить корректную связь не удалось, просмотрщик
показывает диагностику; требуется исправление расположения. Такой маршрут
не считается успешно проверенным.

## Проверка полноты

Для каждого включённого репозитория проверь точки входа, основные ответственности,
владельцев состояния, контракты и взаимодействия. Убедись, что обзорные сценарии
объясняют его роль, а внутренние позволяют изучить реализацию. В UI проверь
основные действия и обработчики; для других видов таргета — соответствующие
публичные входы. Запиши намеренно неохваченные области.

Отдельно осмотри раскрытые контейнеры. Длинное описание без внутренних участников
и связей не даёт изучить архитектуру. Не выравнивай число узлов искусственно:
разные репозитории имеют разную сложность. Проверяй достаточность содержания
для поставленных вопросов и одинаковое качество объяснений по всей карте.
