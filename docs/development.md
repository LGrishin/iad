# Развитие каркаса

IAD Kit содержит универсальные механизмы, правила и пустую заготовку. Готовые карты
и исходники исследуемых проектов находятся за его пределами. Изменение инструмента
должно улучшать последующие построения в разных доменах.

Если пользователь показывает дефект конкретной диаграммы в задаче развития IAD,
сначала определи общее нарушенное требование. Уточни нормативные правила,
авторскую инструкцию, шаблон или схему; при дефекте отображения исправь просмотрщик.
Проверь воспроизведение на временных данных. Саму представленную карту изменяй
только в рамках соответствующего запроса. Прочтение её данных для диагностики
не требует заполнения или пересборки внешнего каталога.

## Границы компонентов

Ядро написано на Python stdlib и обычном JavaScript. HTML/CSS/JS, схемы,
нормативные правила и `iadkit/templates/project/` поставляются вместе с пакетом.
`init` использует этот пустой шаблон и задаёт только метаданные проекта и
закреплённую ревизию источника. Не дублируй заготовку в строках Python и не добавляй
в неё готовые модули, сценарии, основания или архивы файлов.
Защита путей отклоняет создание, сборку и парное сравнение в каталогах самого
каркаса. Проверяй её вместе с неизменной пустотой исходного шаблона.

Формальные JSON Schema проверяются встроенным валидатором поддержанного набора
ключевых слов; это не универсальная реализация JSON Schema. Неизвестный ключ схемы
и внешняя ссылка `$ref` вызывают ошибку, сеть не используется. Версия контракта
меняется при несовместимом изменении авторских данных. Схемы, загрузку, проверки,
просмотрщик, сравнение и документацию обновляй согласованно.

Новый язык или способ извлечения фактов может использовать отдельный адаптер,
выдающий канонические данные. Названия проектов и их частные эвристики не добавляй
в сборщик. Репозиторий и веб-хост задаются путями и `webUrlTemplate`.

## Временные данные для проверок

Проверки создают настоящие Git-репозитории, авторские данные и сборки во временных
каталогах вне каркаса. Они должны охватывать разную структуру: одиночный репозиторий,
набор репозиториев, вложенные группы, развилки и две версии. Это данные проверки,
а не поставляемые законченные диаграммы. Не привязывай регрессии к конкретным именам,
SHA, файлам или доступности пользовательского проекта.

Из корня каркаса выполни:

```sh
python3 -m unittest discover -s tests -v
python3 tests/smoke.py
```

Smoke-проверка создаёт необходимые данные, собирает их одним ядром и запускает
проверки проигрывателя и геометрии. Для реальных браузерных действий:

```sh
python3 tests/smoke.py --browser
```

Временные исходники, данные и сборки удаляются после проверки. В браузерном режиме
профили Chrome, скриншоты и отчёты также создаются внутри временного каталога.
Для Node-проверок нужен Node 22+, для браузера — локальный Chrome. На macOS путь
к нему выбирается по умолчанию; на другой системе задай `IAD_CHROME_BINARY`.
Браузерный набор использует изолированный профиль, DevTools Protocol и отключённую
сеть; дополнительные npm-пакеты не требуются.

Для отдельной геометрической проверки можно передать собранную модель, например
во временном каталоге:

```sh
node tests/player.mjs
node tests/layout.mjs
node tests/ports.mjs
node tests/routing.mjs /path/to/build/model.json
```

Браузерные инструменты также принимают явные пути:

```sh
node tests/browser.mjs /path/to/build/index.html
node tests/hierarchy-browser.mjs /path/to/hierarchy/build/index.html
node tests/comparison-browser.mjs /path/to/comparison/build/index.html
```

Это инструменты проверки определённых структурных случаев. Базовому браузерному
набору нужны несколько сценариев, развилка и основания; иерархическому —
равноправные контейнеры, вложенный сценарий с ветвью и другой многошаговый локальный
процесс. Эти условия относятся к тестовому набору, а не к минимально допустимой
карте. Для полной проверки изменений используй `smoke.py --browser`, который
создаёт подходящие данные сам.

Python-проверки оценивают закреплённую версию при изменённом рабочем дереве,
архивы и строки исходников, ссылки, графы, ошибки CLI, встраивание данных и
воспроизводимость сборки. Геометрические проверки оценивают пути, порты и подписи.
Браузер проверяет реальные элементы и события: раскрытие контейнеров по шапке,
панорамирование из свободного места внутри, независимое действие дочерних карточек,
клик и клавиатуру у точек API, компактные и двумерные раскладки,
каталог уровней, решения и прогресс, код, вопросы, сравнение и узкий экран.
Регрессии также проверяют сохранность авторских входов при совпадении с выходами,
полноту манифеста для символических ссылок, числовое переполнение JSON,
нумерацию исходников по LF, начальную вложенную область, явные API-контракты
и сценарии со сходящимися ветками без экспоненциального разворачивания путей.
Визуальную оценку дополняй просмотром скриншотов. Тесты не доказывают смысл
архитектурных выводов; доступность файла не заменяет чтения кода.

## Сохраняемые возможности

При изменениях должны оставаться доступными короткие описания и раскрываемые
подробности, объяснения данных и операций, вложенные диаграммы, читаемые стрелки,
сценарии с независимым прогрессом и ветвями. Сохраняй метаданные репозиториев,
точные коммиты и строки, офлайн-просмотр полных файлов, серверные ссылки,
копируемые вопросы для шагов и участников и сравнение версий. Полный перечень
согласованных требований ведётся в [единых правилах](../iadkit/spec/iad-rules.md).

Реальные записи исполнения, параллельные маршруты и автоматическое извлечение
моделей двух Git-версий потребуют явных контрактов адаптеров и новых проверок.
Автоматизация синтаксических ссылок не должна повышать статус семантического
подтверждения без подходящей проверки.
