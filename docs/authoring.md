# Заполнение проекта агентом

Эта инструкция применяется к запросу построить или обновить конкретную карту.
Она описывает заполнение данных для готового каркаса. Точные требования находятся
в [единых правилах IAD](../iadkit/spec/iad-rules.md), структура — в
[формате](format.md). В задаче развития инструмента используй
[порядок изменения каркаса](development.md): переданная для разбора карта сама
по себе не становится объектом редактирования.

## Каталог и пустая заготовка

Пользователь может по желанию указать папку для диаграммы. Используй этот путь;
фиксированного каталога по умолчанию нет. Если путь не указан, выбери подходящую
папку вне IAD Kit с учётом рабочей области и сообщи итоговый путь. Каждая диаграмма
хранится в отдельном каталоге и может охватывать несколько репозиториев.
Репозиторий каркаса остаётся отдельным и не заполняется картами.

Выбирай устойчивое имя и проверяй принадлежность существующих данных перед
обновлением. При переносе пересчитывай относительные `repositories[].path`.
Для каждого репозитория сохраняй отдельный полный SHA; `primaryRepository`
задаёт основную точку отсчёта и не ограничивает состав карты.

Создай новый каталог командой `iad init <diagram-dir> --repo <repository>`
из корня каркаса либо через `python3 -m iadkit`. Команда использует
[пустой шаблон](../iadkit/templates/project/), закрепляет метаданные и SHA.
Категории `nodes`, `edges`, `contracts`, `scenarios`, `evidence` остаются пустыми;
их содержимое получи из исходников. Готовых образцовых карт в поставке нет.
Пустая заготовка намеренно не проходит проверку содержательной диаграммы.

## Порядок работы

Сначала изучи исходники и назначение проекта. Зафиксируй высокоуровневое описание:
модули, ответственности, связи, основные сценарии от входа до результата
с передачей управления и данных. Только после этого детализируй узлы, контракты
и шаги: добавляй описания, ссылки на код и вызовы. Новые факты учитывай в общей модели.

Под модулем понимай часть проекта с самостоятельной задачей и определённым
способом взаимодействия с другими частями. Укажи его назначение, входные данные
или команды и результат. Граница модуля определяется ответственностью;
он может включать несколько файлов и классов.

До создания `nodes/` отфильтруй найденные в коде сущности. Для каждого кандидата запиши ответственность, границу, фактическое взаимодействие и решение. Количество прочитанных файлов и классов не задаёт число узлов.

| Найдено в коде | Представление в IAD |
| --- | --- |
| Компонент/модуль с собственной ответственностью и контрактом | Узел с фактическим именем из кода/каталога, объяснением роли и источниками |
| Настройки, схема, DTO, параметры, пути | Вход/результат операции, данные или пояснения типов владельца |
| Пример, демонстрационный класс, экземпляр | Пояснение реализации и ссылка на код; точка расширения показывается общим контрактом |
| Вспомогательная функция внутри CLI/клиента | Внутренняя операция владельца; отдельный узел требует самостоятельной архитектурной границы |
| Toolchain, пустые каталоги, сборка/CI/тесты продукта | Сопроводительная документация; отдельная карта только при заданной области инфраструктуры |

Пересматривай всю модель при замечании к такому классу ошибок. Не сохраняй конфиг на полотне под новым именем «обработчик настроек» без реальной самостоятельной ответственности. Формальные проверки не заменяют этот смысловой просмотр.

1. Определи границы таргета и ревизии, сохрани полные SHA. Прочитай инструкции
   исходных репозиториев, изучи назначение проекта, структуру кода, точки входа, основные модули
   и последовательность их взаимодействия в основных сценариях. Зафиксируй
   высокоуровневое описание архитектуры до детализации. Не анализируй
   незакоммиченный код как часть выбранных версий. Для нескольких репозиториев
   сначала подготовь план контейнеров и уровней по [правилам вложенности](hierarchy.md).
2. Заполни `project.json`: имя, таргет, репозитории, версии, границы и ограничения.
   Пути относительны каталогу данных; для другой машины используй `--repo ID=PATH`.
   Адрес файла на сервере задаётся `webUrlTemplate`, например
   `https://github.com/org/repo/blob/{revision}/{path}#L{line}` или
   `https://gitea.example/org/repo/src/commit/{revision}/{path}#L{line}`.
   Сохрани доступные сведения о репозитории. Если сервера нет, ссылку опусти.
3. Создай `nodes/*.json` из отобранных ответственностей. Группа выражает архитектурную ответственность, а не общую папку примеров или рабочих файлов. Названия участников и интерфейсов бери из изучаемого кода или каталогов: пакет/crate, модуль, класс, интерфейс. Сохраняй регистр и разделители; не подменяй `bcs-client` переводом или описанием назначения. Редкое исключение допустимо для слишком сложного имени или отсутствия применимого имени; запиши причину и оригинал, если он известен. Совпадающие имена различай владельцами либо точным квалифицированным именем.
   Роль объясни в 1–2 коротких предложениях, подробности вынеси в `details`.
   Для каждого элемента данных во владении и каждой операции укажи назначение;
   типы, параметры и жизненный цикл поясни отдельно. Различай собственное состояние,
   временные значения и заимствованные ссылки. Привязывай имена к коду или
   связанным участникам. Проверяй ясность всех карточек, а не одного модуля.
4. Опиши контракты, связи и самостоятельные сценарии по назначению таргета.
   Для UI это могут быть действия пользователя, для сервиса — API-запросы,
   для CLI — команды, для библиотеки — публичные операции. Выбери фактические
   входы по коду; не добавляй авторизацию, рендеринг или другой предметный процесс
   без основания в проекте. Укажи `scope` и `trigger`; внутренние процессы
   размести в областях владельцев. У каждого шага объясни вход, действие и
   результат; у каждой ветви — условие и конечный исход. Повторные обращения
   к модулю показывай отдельными шагами. Цикл агрегируй в конечный маршрут.
   ID сохраняй при переименованиях. Связи и шаги привязывай к фактическому API через
   `targetContract` и при необходимости `sourceContract`; значения — ID контрактов.
   При нескольких интерфейсах не оставляй привязку неоднозначной. Неопределённый
   контракт обозначай как неизвестный, не придумывай методы для оформления стрелки.
5. В `evidence` добавь точные места кода. Объявление подтверждает тип или контракт;
   вызов — передачу управления; регистрация — подключение обработчика. Для каждого
   основания заполни `support.kind`, `support.status` и необходимое пояснение.
   Для шага и связи отдельно заполни `verification`. `reviewed` означает, что автор
   прочитал подходящий код и проверил конкретное утверждение. Наличие файла или
   корректный SHA этого не доказывают. Неизвестное фиксируй явно.
6. В `view.json` настрой корневой порядок, начальный сценарий, интервалы и тему.
   Не вноси эти настройки в JavaScript. Допустимы отдельные JSON-файлы на сущность
   или массивы по темам. HTML не редактируй. Сохрани исключение `build/`
   из контроля версий каталога карты.
7. Выполни `validate`, исправь ошибки и изучи предупреждения. `--strict`
   отклоняет также предупреждения; обычная сборка допускает черновую карту с явным
   статусом. Выполни `build`. Для офлайн-переноса можно сохранить созданный
   `sources.json` как `snapshots.json` и указать его в `sourceArchive`.
8. Проверь карту в браузере. Осмотри краткие карточки и раскрываемые подробности
   всех участников. Открой каждый крупный контейнер: внутри должна появиться
   читаемая диаграмма с собственными связями. Простые небольшие группы должны
   располагаться компактно по вертикали. Проверь сворачивание только по шапке,
   перетаскивание из свободного места и независимость дочерних действий. Открой
   API на контуре компонента и большого модуля мышью и клавиатурой: операции,
   потребители и источники должны соответствовать данным. Пройди успешные и отказные
   ветви, смену решения, перемотку, переключение уровней и возврат к сценарию.
   Проверь сохранение прогресса, интервалы, подписи и стрелки при разных масштабах
   и ширине окна. Структурная проверка не оценивает ясность и истинность описаний.
9. Открой код из шага и карточки участника: проверь коммит, путь, строки, полный
   файл, переход к репозиторию и к файлу на сервере, если ссылки настроены.
   Проверь копируемые заготовки вопросов в конце карточки каждого участника
   и каждого шага: проект, версия, сценарий, шаг и решения должны быть однозначны.
10. Передай каталог данных, HTML, команду просмотра и отчёт. Назови версии,
    ограничения, предупреждения и статус семантической проверки. Обратную связь
    о правилах IAD точно сохраняй в `iadkit/spec/iad-rules.md`, включая одобренные
    возможности. Не меняй общий интерфейс как побочный способ заполнить карту.

При обновлении исходников меняй SHA и основания совместно, затем пересобирай
архив. Сборщик не переписывает архитектурные выводы за автора и не обновляет версии
молча. На другой машине SHA-256 подтверждает целостность архива; без Git checkout
сам архив не доказывает происхождение из указанного коммита.
