# Формат данных IAD v1

Формальная структура находится в `iadkit/schemas/`. `schemaVersion: 1` относится к
авторским данным и модели. `manifest.kitVersion` определяет версию сборщика.
`manifest.project` хранит ID и имя проекта, `target` — выбранную область карты,
`settings` — значимые настройки просмотра.
Поддерживаемые версии проверяются явно. Данные другого формата требуют явного
преобразования в канонические сущности и не принимаются автоматически.

## Авторский каталог

```text
project.json
view.json
nodes/*.json
edges/*.json
contracts/*.json
scenarios/*.json
evidence/*.json
snapshots.json          # необязательный архив точных исходников
```

Каталог данных находится вне репозитория IAD Kit. Команда `init` создаёт его из
`iadkit/templates/project/` и закрепляет метаданные источника; пять категорий
сущностей остаются пустыми до анализа кода агентом. Шаблон не содержит готовой
диаграммы. `AUTHORING.md` в созданном каталоге поясняет заполнение, а `.gitignore`
исключает результат `build/` из контроля версий.

В каждой категории файл содержит одну сущность либо массив. Файлы читаются в
лексикографическом порядке; порядок элементов массива сохраняется. ID уникальны
в своей категории. ID шагов уникальны внутри сценария, вариантов — внутри развилки.
Разбиение по файлам предназначено для удобства редактирования и не задаёт архитектуру.
JSON с повторяющимися ключами, `NaN`, `Infinity` или числом, переполняющим конечный
Python `float` (например, `1e999`), отклоняется при чтении. Это правило применяется
также к `comparison.json` и архиву исходников.

| Сущность | Основные поля |
|---|---|
| Проект | `schemaVersion`, `id`, `name`, `primaryRepository`, `repositories`; дополнительно `target`, `metadata`, `limitations`, `sourceArchive` |
| Репозиторий | `id`, `path`, полный `revision`; дополнительно `url`, `webUrlTemplate`, `included`, `scope` |
| Узел | `id`, `label`, короткий `role`; `parent`, `kind`, `repository`, `details`, `sources`, `ownedData`, `typeExplanations`, `ownershipNote` |
| Данные во владении | `name`, `description`; `type`, `details`, `sources`, `target` — ID связанного узла |
| Контракт | `id`, `node`, `name`, `operations`; `description`, `sources` |
| Операция | `name` — сигнатура, `description` — краткое назначение, `input`, `output`; `details`, `errors`, `sources` |
| Связь | `id`, `from`, `to`, `label`, `kind`, `sources`, `verification`; `contracts`, `sourceContract`, `targetContract` — явные точки API |
| Сценарий | `id`, `title`, `goal`, `entry` — ID первого шага, `steps`; `scope`, `trigger`, `overviewReason`, `preconditions`, `mode`/`basis` |
| Шаг | `id`, `from`, `to`, `title`, `input`, `action`, `output`, `next`; `kind`, `sources`, `contracts`, `sourceContract`, `targetContract`, `nuance`, `branch`, `verification` |
| Вариант ветки | `id`, `label`, `condition`, `result`, `next` |
| Основание | `id`, `repo`, `revision`, `path`, `line`, `symbol`, `support` |

Полный перечень обязательных полей и типов задают JSON Schema. `sources` всегда
содержит ID оснований, а не произвольные строки путей. `next: null` завершает маршрут.
У развилки переходы задаются в `branch.options`; обычный `next` не задаёт альтернативное
продолжение. Все шаги должны быть достижимы из `entry`, все варианты — конечны.
Цикл реальной программы описывается конечным сценарием одного прохода/итерации.

Произвольные дополнительные поля содержательных сущностей сохраняются для
расширений. Это не означает, что просмотрщик умеет их отображать. Настройки `view`
проверяются строго, чтобы опечатка в имени параметра не исчезла незаметно.

`node.label` и имя именованного интерфейса/контракта соответствуют фактическому
имени в закреплённой версии кода или каталога, включая регистр, дефисы и
подчёркивания. Назначение объясняется в `role`/`description`, подробности —
в `details`. Для редкого исключения (слишком сложное имя либо отсутствие
подходящего имени) укажи причину и известный оригинал в подробностях или
авторском обосновании. Стабильный `id` не меняется при исправлении подписи.
Это смысловая проверка по источникам: формат не угадывает имя по строкам кода.

## Категории участников

`node.kind` описывает архитектурного участника (например, `module`, `component`, `service`, `storage`, `external`, `actor`, `extension-point`). Явные категории входных данных и артефактов — `config`, `configuration`, `settings`, `schema`, `dto`, `payload`, `parameter`, `data`, `file`, `directory`, `path`, `example`, `instance`, `environment` — не являются допустимыми участниками полотна: семантическая проверка сообщает `architecture.non_participant`. Их содержимое размещается в существующих `input`/`output`, параметрах операций, `ownedData`, `typeExplanations` и источниках. Имена и пути сами по себе не классифицируются автоматически; ответственность узла проверяет автор.

Также отклоняются синонимы `artifact`, `data-object`, `example-instance`;
регистр и разделители `_`/`-` при проверке категории не различаются.

## Настройки просмотра

```json
{
  "rootOrder": ["client", "service", "storage"],
  "initialScenario": "submit-request",
  "layout": {
    "columns": 2,
    "cardWidth": 320,
    "columnGap": 120,
    "rowGap": 140,
    "childGap": 22
  },
  "theme": {"preset": "red-black-gold", "colors": {"--gold": "#b9a06c"}}
}
```

`rootOrder` содержит корневые узлы; остальные идут следом в порядке загрузки.
`cardWidth` — ширина карточки, `columnGap` — свободное место между карточками.
Минимальный промежуток между корневыми карточками — 40 px. При глубоком раскрытии
границы группы растут под двумерную диаграмму с обычными карточками
(минимум 240 px, ширина по умолчанию 285 px).
Для небольших простых групп без явного корневого `columns` просмотрщик выбирает
одну колонку и более плотный промежуток. Явный `rowGap` сохраняется и в таких
группах; `columns` управляет обзором, внутренние области выбирают собственную
раскладку. На узком экране число обзорных колонок ограничивается двумя. Цвета принимаются только
для перечисленных в схеме CSS-переменных; значения — шестнадцатеричные цвета.
Тема по умолчанию не требует `colors`. HTML или JavaScript из данных не исполняются.

## Происхождение и смысл подтверждений

Сборщик добавляет основанию `sourceKey`, серверный `url` либо `null`, и `sourceIntegrity`:

| `sourceIntegrity.status` | Что подтверждено |
|---|---|
| `git-verified` | Текст прочитан из файла по точному Git SHA |
| `archive-verified` | Идентичность и SHA-256 архивного текста проверены; Git checkout для сверки недоступен |
| `unavailable` | Текст не получен; это ошибка сборки |

Архив — объект с ключами `repo@revision:path`. Значение содержит `repo`, `revision`,
`path`, `text`, `sha256`. При доступном Git архив дополнительно сверяется с ним.
Испорченный архив не игнорируется даже при доступном Git; отсутствие файла в
доступном коммите не маскируется архивом. Строки нумеруются с 1 и проверяются по
точному снимку. Граница строки — LF (`\n`); CRLF имеет ту же нумерацию.
Unicode-разделители и form-feed внутри текста не добавляют номера строк,
завершающий LF не создаёт дополнительную пустую строку. Изменения рабочего дерева
не подменяют закреплённый исходник.

Смысл описанного утверждения задаёт автор:

```json
{
  "support": {
    "kind": "callsite",
    "status": "reviewed",
    "note": "Здесь RequestHandler.submit вызывает TaskQueue.enqueue до возврата ответа."
  }
}
```

`support.kind`: `callsite`, `registration`, `declaration`, `implementation`, `trace`,
`reference`. `implementation` нужен для тела реализации: присваивания, проверки
условия, возврата значения. `reference` — общий указатель, который сам по себе не
доказывает утверждение. Статусы: `reviewed`, `unreviewed`, `uncertain`. Шаги и связи
имеют отдельное `verification: {"status": ..., "note": ...}` — проверен ли весь вывод.
Тип шага `kind` уточняет утверждение: `call`, `stage`, `event`, `operation`, `decision`,
`return`, `data`. Вызов требует подходящего основания вызова, регистрации или трассы;
одно объявление или наличие файла этого не доказывает. Валидатор проверяет наличие
и совместимость меток, но не заменяет чтение кода.

Режим v1 — объяснение по коду. Значение `trace` зарезервировано: текущий сборщик отклоняет его с `trace.unsupported`,
даже при наличии метаданных запуска. Для такого режима нужен отдельный адаптер.

## Результат сборки

`model.json` содержит `schemaVersion`, `manifest`, `view`, узлы, связи, контракты,
сценарии, основания и ограничения. `manifest.json` дублирует манифест для внешних
инструментов. `sources.json` содержит ровно использованные полные файлы.
`index.html` включает модель, снимки и общее ядро: внешние CDN не нужны.
`report.json` содержит ошибки/предупреждения и итоговый статус. Нормальная сборка
допускает предупреждения; `--strict` завершает команду с ошибкой и не создаёт новую
сборку. Существующий результат от предыдущей сборки при ошибке может остаться на
диске — всегда проверяй код завершения и отчёт команды.

Выходные файлы не могут совпадать с входами проекта, включая `rules` и
`sourceArchive`; совпадения через символические и жёсткие ссылки также отклоняются
до записи результатов. `manifest.inputs` содержит SHA-256 всех прочитанных входов
под их именами относительно каталога диаграммы, включая JSON через внешние
символические ссылки. Абсолютные пути к этим внешним файлам не публикуются.

Сравнение снимков сопоставляет авторские описания с устойчивыми ID и ищет первое
различие шагов/контрактов по обходу веток. Оно не определяет изменение поведения
только по разнице исходных файлов и не строит архитектуру автоматически.


## Иерархия и область сценариев

`node.repository` содержит ID репозитория и наследуется по `parent`. Для набора
репозиториев каждому включённому исходному репозиторию соответствует корневой узел
`kind: "repository"`. Внутренние модули принадлежат этому контейнеру; внешние контракты
могут иметь отдельный репозиторий зависимости.

`scenario.scope` — ID области карты либо `null` для обзора; `trigger` содержит
`kind: user | system | developer | internal`, необязательные `label` и `sources`.
Для `repository-set` эти метки позволяют проверить уровни и назначение каталога.
`view.initialScope` задаёт начальный контекст, по умолчанию обзор. При открытии
раскрываются выбранная область и родители участников начального шага. Подробнее:
[уровни, покрытие и вложенные диаграммы](hierarchy.md).

Чистый модуль `IADLayout` рассчитывает координаты всех уровней по полной структуре
связей. Простые небольшие группы могут располагаться вертикально и плотнее;
сложные сети используют несколько колонок с проходами. Переключение сценария
не меняет выбранную раскладку. `childGap` сохранён для чтения старых настроек.
Карточки на вложенных уровнях имеют обычный размер, а контейнер растёт под их
расположение; вертикальная цепочка остаётся диаграммой со связями.

Автоматическая компактная раскладка применяется к группе до пяти участников без
циклов и с не более чем двумя соседями у каждого, в том числе к независимым
карточкам. Анализ учитывает все связи и шаги всех сценариев, проецируя вложенные
узлы на рассматриваемый уровень. По умолчанию интервал между карточками — 76 px,
отступ внутри компактного контейнера — 48 px. Явный `layout.rowGap` сохраняется;
`layout.columns` отключает автоматический выбор одной колонки для корня.

## Точки API и привязка связей

Контракт задаётся сущностью `contracts` с `id`, предоставляющим `node`, названием,
операциями и источниками. В `edge` и `step` укажи `targetContract`, когда получатель
предоставляет вызываемый API. `sourceContract` указывает API исходящего участника,
если это соответствует реальному взаимодействию. Значения — ID существующих
контрактов. Не подменяй ими доказательство вызова: для действия по-прежнему нужны
свои основания в коде.

Владельцем явного интерфейса может быть сам участник либо его контейнер-предок.
В последнем случае стрелка привязывается к границе владельца API, а исходный
компонент сохраняется в сведениях об использовании. На обзоре систем описывай
взаимодействие контейнеров и их внешние контракты; подробные вызовы компонентов
показывай в соответствующих сценариях. Не придумывай внешний интерфейс только
ради переноса внутренней стрелки на рамку репозитория.

Поле `contracts` у шага и связи сохраняется для ссылок на относящиеся контракты; однозначную
привязку к участникам просмотрщик может использовать как запасной вариант, если
владелец охватывает только один конец связи. Контракт общего предка обоих концов
остаётся контекстной ссылкой и не превращает внутреннюю связь в вызов контейнера
самому себе. Для
нескольких API одного участника задавай явные поля, чтобы не выбирать API по имени,
направлению стрелки или порядку элементов.

Просмотрщик формирует устойчивые маркеры предоставления и использования API на
контуре карточек, включая раскрытые контейнеры. Координаты маркеров не являются
авторскими данными. При скрытом владельце контракт проецируется на видимого предка,
сохраняя настоящего предоставляющего участника. Нажатие на маркер показывает API,
потребителей, операции и источники. Для отношения без определённого контракта
используется отдельно обозначенный маркер «API не указан» с известными сведениями
о связи. Такой маркер не означает наличие публичного API в исходниках.
