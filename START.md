# Начать работу с IAD

IAD — **Interactive Architecture Diagram**, интерактивная архитектурная диаграмма.

Пользователю достаточно передать агенту путь к исходникам и этому файлу:

```text
Построй IAD проекта /path/to/project.
Следуй /path/to/iad-kit/START.md.
```

Для многорепозиторной карты перечисли несколько путей или укажи охватывающий
их каталог и нужную область. Можно задать имя диаграммы, версии и сценарии.
Для обновления укажи имя существующей карты. Для сравнения — две версии
или попроси подобрать содержательное изменение.

Папку для диаграммы можно указать по желанию, например добавив к запросу:

```text
Каталог диаграммы: /path/to/diagrams/my-map
```

Фиксированного каталога по умолчанию нет. Если путь не указан, агент выбирает
подходящую папку вне репозитория IAD Kit с учётом рабочей области и сообщает
итоговый путь. Каждая диаграмма хранится в отдельном каталоге и может охватывать
несколько репозиториев.

## Граница задачи

Этот файл описывает построение и обновление карт. Сам репозиторий IAD остаётся
общим инструментом с пустым [шаблоном](iadkit/templates/project/).
Если пользователь развивает IAD и показывает диаграмму для обсуждения качества,
используй её как материал проверки общих правил, шаблонов и просмотрщика.
В таком случае работай по [AGENTS.md](AGENTS.md); построение или изменение
конкретной карты должно входить в запрос, а не следовать из наличия ссылки на неё.

## Инструкция агенту для построения карты

Доведи запрос до проверенной HTML-карты и способа её открыть. Прочитай необходимые
правила самостоятельно; ссылки ниже относятся к каталогу каркаса.

1. Прочитай [AGENTS.md](AGENTS.md), [правила IAD](iadkit/spec/iad-rules.md),
   [порядок заполнения](docs/authoring.md), [формат](docs/format.md) и
   [уровни и вложенность](docs/hierarchy.md). Учитывай инструкции исходных
   репозиториев. Формальные схемы находятся в `iadkit/schemas/`, пустая заготовка —
   в `iadkit/templates/project/`. Заполненной карты в поставке нет.
2. Определи исходные Git-репозитории и границы диаграммы из запроса. «Текущий проект»
   означает корень его Git-репозитория. Если рабочий каталог — сам IAD Kit,
   не считай его изучаемым проектом без основания в запросе. Если исходники
   определить нельзя, уточни путь. По умолчанию охвати весь указанный проект.
   Для каждого заданного репозитория используй `HEAD`, если версия не указана,
   и зафиксируй полный SHA до анализа. Версии внешних зависимостей бери из
   закреплений изучаемого проекта.
3. Используй каталог диаграммы, если пользователь указал его в запросе.
   Иначе выбери подходящий каталог вне IAD Kit с учётом рабочей области;
   фиксированного пути по умолчанию нет. Сообщи выбранный путь в результате.
   Имя должно устойчиво описывать область карты и не обязано совпадать с именем
   репозитория. Каждую карту, в том числе многорепозиторную, храни в отдельном
   каталоге. При общем каталоге для набора карт создай отдельную подпапку.
4. Проверь существующие данные. Перед обновлением сверь таргет и исходные
   репозитории; если имя занято другой картой, выбери отдельное имя. При обновлении
   сохраняй устойчивые ID, полезные пояснения и предпочтения. Переданную карту
   используй как основу только для запрошенного построения или обновления,
   проверив версии. При переносе пересчитай относительные `repositories[].path`
   и сохрани идентичность снимков исходников.
5. Новый пустой каталог создай через `init`, указав основной репозиторий.
   Команда копирует пустой шаблон и закрепляет метаданные; содержательный анализ
   выполняешь ты. В `project.json.repositories` добавь остальные репозитории
   с отдельными ID, путями и полными SHA. `primaryRepository` задаёт точку отсчёта,
   а не ограничивает карту одним репозиторием. Существующие данные редактируй
   напрямую: отдельной команды `update` нет.
6. Самостоятельно изучи исходники, назначение проекта и структуру кода.
   Зафиксируй высокоуровневое описание: модули, ответственности, связи,
   основные сценарии от входа через взаимодействие модулей до результата.
   Только после этого добавляй подробные описания, контракты, ссылки на код
   и конкретные вызовы. Выводы подтверждай кодом, неясности обозначай явно.
7. Отфильтруй архитектурных участников по ответственности, границе и реальному взаимодействию; файлы/классы не превращаются в узлы автоматически. Конфиги, Settings, схемы, DTO и пути показывай во входах/данных владельца, примеры — в пояснениях к общему контракту расширения. Не добавляй окружение и рабочие каталоги в runtime-архитектуру. Затем задай уровни и владельцев. Для набора репозиториев создай
   равноправные контейнеры и внутренние модули каждого. Подбери сценарии по
   назначению таргета: действия пользователя, API-запросы, команды CLI или
   операции библиотеки. Назначь `scope` и фактический `trigger`; внутренние циклы
   и фоновые задачи размещай в соответствующих областях. Не копируй сценарии
   из другого домена только ради заполнения обзора.
8. Детализируй высокоуровневое описание по выбранным ревизиям: заполни узлы, данные во владении, контракты, связи,
   самостоятельные сценарии и основания. Участников и интерфейсы называй как
   в коде или каталогах, сохраняя исходное написание; назначение поясняй в роли.
   Редкие исключения для сложных или отсутствующих имён обоснуй, сохранив
   оригинал, если он известен. Краткая роль — 1–2 предложения;
   подробности отдельно. Объясни каждый элемент данных, операцию и параметр.
   Проверь условия и результаты ветвей по коду. Основания должны поддерживать
   конкретные утверждения, а доступность файла не означает их истинности.
   При обновлении SHA пересмотри затронутые источники и статусы проверки.
9. Настрой `view.json`: корневой порядок, начальный сценарий, интервалы и тему.
   Содержимое задаётся данными, интерфейс уже реализован. Сохрани исключение
   `build/` из контроля версий каталога карты. Выполни `validate`, исправь ошибки,
   затем `build`. Стремись к `validate --strict`; неопределённости и оставшиеся
   предупреждения назови явно.
10. Открой результат в браузере. Проверь краткие карточки и подробности всех
   участников, раскрытие контейнеров по шапке, перетаскивание внутри, точки API,
   компактную раскладку простых групп, уровни каталога, сценарии и
   ветви, перемотку, стрелки при разных масштабах, встроенный код, переходы
   к точным исходникам и копирование вопросов у шагов и участников. Если браузер
   недоступен, прямо укажи невыполненную проверку.
11. Передай путь к готовому `index.html`, команду просмотра, область карты, SHA
    каждого репозитория и существенные ограничения. Обратную связь о формате
    сохраняй в единых правилах IAD, не подменяя задачу построения новой функцией ядра.

Для сравнения подготовь отдельную внешнюю диаграмму с `before/`, `after/` и
`comparison.json` по [инструкции сравнения](docs/comparison.md).

## Команды

Команды выполняются из корня IAD Kit. `<diagram-dir>` — внешний каталог выбранной
карты. `init` нужен только для нового отсутствующего или пустого каталога:

```sh
python3 -m iadkit init "<diagram-dir>" --repo "<primary-repository>" --revision "<ref>"
```

После анализа и заполнения данных:

```sh
python3 -m iadkit validate "<diagram-dir>"
python3 -m iadkit build "<diagram-dir>"
python3 -m iadkit preview "<diagram-dir>" --port 8010
```

`preview` пересобирает карту и служит по адресу `http://127.0.0.1:8010/` до Ctrl+C.
Если порт занят, выбери свободный и сообщи точный адрес. Готовый
`<diagram-dir>/build/index.html` открывается в Chrome также без сервера и сети.
